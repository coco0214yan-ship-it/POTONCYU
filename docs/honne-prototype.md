# 本音から会話を始める試作

## PCで試す

プレビュー用サーバーを起動した状態で、http://127.0.0.1:4173/?demo=1 を開きます。Googleログイン風のボタンから仮の名前で入り、グループを作成します。

サーバーを起動し直す場合は、この `coco` フォルダでPowerShellを開き、`node server.js` を実行します。`server.js` は既存のPC内開発用ファイルで、GitHubへの公開対象にはしません。

## 変更した体験

- 伝えたいことを1〜500字で自由入力し、生成された穴あき一首の3行目を4択から選んで完成させます。
- 下書きはメモリ上だけに保持し、ルーム・メッセージ・localStorageには保存しません。書き直しでは同じ下書きに戻れます。送信・ログアウトで破棄します。
- AI接続時は入力をOpenAIへ送り、穴あき一首と各4択を3セット生成します。APIには `store: false` を指定します。生成された一首が完全に入力の意図を保っている保証はないため、送信前に必ず本人が読みます。
- ガチャの演出を最低1.7秒はさみ、真ん中に入れる5音のことばを4択から選びます。ことばが落ちる演出を約1秒、完成した一首を読む余韻を約1秒はさんで送信確認を出します。引き直し・選び直し・書き直しができます。
- 主なチャットに届くのは一首だけです。相談文をお題・メタデータ・通知へ流用しません。
- リアクション候補と音のUIを外し、「この一首から話す」を中心にしました。一首ごとの文章トークは同じルームの全員が閲覧できます。個別の秘密のトークではありません。
- 既存の一首とトーク履歴、お気に入りは削除しません。旧リアクションの処理は互換性のためコード内に残しますが、新しいUIからは使いません。

## 12時間のぽとん

今回は時間制限なしが標準です。ルーム作成時の「時間のルールを試す（任意）」を開き、自分でオンにした場合だけ制限がかかります。オンの場合はルーム作成時を起点に24時間ごとに新しい回が始まり、最初の12時間だけ1人1首送れます。途中参加でも締切は同じです。受付終了後や送信済みでも、一首ごとの文章トークは続けられます。

24時間後はアプリ内の受付カードが「今日のぽとんが始まりました」に変わり、ルーム一覧にも「今日のぽとん」を表示します。アプリを閉じた状態でスマートフォンへ届くプッシュ通知は、今回まだ実装・稼働していません。罰則や連続記録はありません。

`functions/lib/poem-rounds.js` は画面とサーバーで共通の時間判定です。`sendFeelingPoem` はサーバー時刻とFirestoreトランザクション（まとめて一度だけ保存する処理）で締切と1人1首を確認します。同じ送信IDの再送は重複保存しません。

## 五・七・五・七・七

2026年11月12日、3行目を4択から選ぶ機能を戻し、文字数ではなく読みの音数を検査する形に変更しました。小さい「ゃ・ゅ・ょ」などは前の仮名と合わせて1音、「っ・ん・ー」はそれぞれ1音です。

`functions/lib/feeling-catalog.json` に21パターンを持ち、[Kuromoji](https://github.com/takuyaa/kuromoji.js)で読みを取得して生成した `feeling-catalog-data.js` をブラウザへ配ります。辞書そのものはスマートフォンへダウンロードしません。21パターンの全4択、計84通りが5・7・5・7・7になることをテストしています。表示文字や選択肢を編集したら、`node scripts/build-feeling-catalog.cjs` で読みデータを再生成してから `node scripts/build-preview.cjs` を実行します。

AIの出力もサーバーで辞書の標準的な読みを調べ、本文4行と全4択の音数を検査します。音数が合わない候補、読みを取得できない候補は表示しません。漢字の特殊な読み・人名の読みまでは保証しません。送信時にも選んだことばが3行目と一致することと、完成した一首の音数を再検査し、`selectedWord` と `poemReadings` を保存します。以前の履歴にはこの制約をさかのぼって適用しません。

## AIと本物の通信の状態

現時点では `POTONCHU_FEELING_CONFIG.enabled` は `false` です。試作では `feeling-poems.js` の定型候補を出し、AI未接続と表示します。自由入力をAIが理解して生成している状態ではありません。元の公開サイトとGitHub Pagesのプレビューは、今回変更していません。

本物のAIと通信を有効にする前に、次の作業が必要です。

1. Firebaseの管理ログイン・Functionsを使える契約・OpenAI APIの利用設定を確認する。
2. `OPENAI_API_KEY` をFirebaseのSecret Managerへ登録する。キーはチャット・HTML・JavaScript・GitHubに載せない。
3. 既存のFirestoreルールを確認し、次の制約を既存の許可条件へ組み込む。単に `allow ...: if false` を追加しても、別の許可条件が残っていると制限されない。
4. `generateFeelingPoems` と `sendFeelingPoem` をデプロイし、実際の別端末で会員・非会員・同時送信・締切前後を確認する。
5. それから `POTONCHU_FEELING_CONFIG.enabled` を `true` にして画面を公開する。

必要なFirestoreルールの制約:

- `rooms/{roomId}/messages` への新しい本音モードの直接書き込みは禁止し、`sendFeelingPoem` だけで書き込む。旧クライアントから直接保存して受付・回数制限を回避できないようにする。
- ルームの `poemWindow` と作成時刻を参加後に自由に書き換えられないようにする。
- `rooms/{roomId}/poemRounds` と `_poemGenerationUsage` はクライアントから書き込めないようにする。
- 一首・返信を読めるのは参加者だけにし、一首ごとの返信作成には本人のUID・500字上限・許可フィールドを検査する。

AI生成・サーバー送信はコードとモックによるテストまでです。Firebase Emulatorや本番のルール検証・デプロイ・実際のAI呼び出しは未実施です。
